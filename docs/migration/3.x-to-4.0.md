# Migrating From kRandom 3.x To 4.0

4.0.0 is the major release after 3.2.0, the last 3.x minor release. Under the
[versioning policy](../../VERSIONING.md), only a major release removes public API or changes it
incompatibly, and 4.0.0 does both in a few named places. It also changes seeded output in four places
and the recipe format. This guide lists each change from 4.0.0, what to change in your code, and how to
keep the 3.2 values where you need them. The [changelog](../../CHANGELOG.md) has the full entries.

## Upgrade checklist

1. **Recompile** every module that uses kRandom against 4.0.0. Code compiled against 3.x that calls a
   removed method fails with `NoSuchMethodError`, and code that reads `GenerationRecipe.RECIPE_VERSION`
   has the 3.x value `"v1"` compiled into it.
2. **Replace the removed methods:** `Schema.generateBatch(int)` and `Schema.loop(int)` with
   `nextRecords(int)`, and `SchemaProjection.project(T)` with `projectRow(T)`.
3. **Retype schema records** to `Map<String, @Nullable Object>` if you check nullness with NullAway in
   JSpecify mode, or to `Map<String, Any?>` in Kotlin.
4. **Kotlin `pick`:** check each `krandom.pick(listOf(...))` whose list holds `null`, and each value read
   from a `PickGenerator<*>`.
5. **Tests that assert exact seeded values:** update the expected values, or set the four seeding settings
   to `false` to keep the 3.2 values.
6. **Saved recipes:** a `krandom-recipe/v1` recipe from 3.x no longer replays. Replay it with the 3.x
   release it names, or record a new recipe with 4.0.0.

## Removed: the deprecated schema record methods

`Schema.generateBatch(int)`, `Schema.loop(int)` and `SchemaProjection.project(T)` were deprecated in 3.1.0
and are removed from 4.0.0. Their replacements, added in 3.1.0, return the same records and rows from the
same record sequence, typed `Map<String, @Nullable Object>`:

| 3.x | From 4.0.0 |
|---|---|
| `schema.generateBatch(count)` | `schema.nextRecords(count)` |
| `schema.loop(count)` | `schema.nextRecords(count)` |
| `projection.project(value)` | `projection.projectRow(value)` |

Before:

```java
List<Map<String, Object>> batch = schema.generateBatch(10);
List<Map<String, Object>> more = schema.loop(10);
Map<String, Object> row = projection.project(profile);
```

After:

```java
List<Map<String, @Nullable Object>> batch = schema.nextRecords(10);
List<Map<String, @Nullable Object>> more = schema.nextRecords(10);
Map<String, @Nullable Object> row = projection.projectRow(profile);
```

Code that calls a removed method no longer compiles. A jar compiled against 3.x that calls one fails at
run time with `NoSuchMethodError`, so recompile it rather than only change the dependency version. javac
ignores the `@Nullable`, so `List<Map<String, Object>> batch = schema.nextRecords(10);` also compiles.

## Changed: `Schema` is a generator of nullable records

From 4.0.0 a `Schema` is a `Generator<Map<String, @Nullable Object>>`, where 3.x had
`Generator<Map<String, Object>>`. A record's value is `null` where its provider returns `null`, and the
new type says so. `generate()` is no longer deprecated: it returns the record that `nextRecord()` returns.
The `generateList`, `stream`, `map` and `filter` methods it inherits give the same type. The records and
the seeded values are unchanged, and so are the JVM signatures, so compiled code keeps working.

**Java.** javac ignores the `@Nullable`, so this still compiles with plain javac:

```java
Map<String, Object> record = schema.generate();
Generator<Map<String, Object>> records = schema;
```

NullAway in JSpecify mode rejects both lines from 4.0.0, with `incompatible types: Map<String, @Nullable
Object> cannot be converted to Map<String, Object>`. Declare the new type argument:

```java
Map<String, @Nullable Object> record = schema.generate();
Generator<Map<String, @Nullable Object>> records = schema;
```

**Kotlin** reads a record as `Map<String, Any?>` and a schema as `Generator<Map<String, Any?>>`, so these
3.x lines no longer compile:

```kotlin
val name: Any = schema.generate().getValue("name")
val records: Generator<Map<String, Any>> = schema
```

Handle the `null`, or declare the nullable type:

```kotlin
val name: Any = checkNotNull(schema.generate()["name"])
val nickname: Any? = schema.generate()["nickname"]
val records: Generator<Map<String, Any?>> = schema
```

## Changed: `pick` accepts a list that holds `null`

From 4.0.0 `Krandom.pick(List)`, both `Generators.pick` methods and `PickGenerator<T>` bound `T` by
`@Nullable Object`, so a list that holds `null` can be picked from, and the `null` is returned. Seeded
picks are unchanged, and Java callers call the methods they called before.

**`PickGenerator` keeps a `null`.** In 3.x it copied its source with `List.copyOf`, so a source that held
`null` threw a `NullPointerException`. From 4.0.0 the copy keeps the `null`:

```java
PickGenerator<@Nullable String> picks = Generators.pick(Arrays.asList("a", null));
// 3.x: NullPointerException. From 4.0.0: "a" or null.
@Nullable String value = picks.generate();
```

**Kotlin `pick` of a list with `null`.** In 3.x `krandom.pick(listOf("a", null))` called the varargs
`pick` with the list as its one value, so it returned the list. From 4.0.0 it calls `pick(List)` and
returns an element:

```kotlin
// 3.x
val whole: List<String?> = krandom.pick(listOf("a", null))

// From 4.0.0
val one: String? = krandom.pick(listOf("a", null))
val whole: List<String?> = krandom.pick<List<String?>>(listOf("a", null))
```

The first 3.x line no longer compiles. To pick the list itself as one value, give the type argument, as the
last line does.

**Kotlin `PickGenerator<*>`.** Kotlin reads a star projection through the type parameter's bound, so from
4.0.0 a value from a `PickGenerator<*>` is `Any?`:

```kotlin
val generator: PickGenerator<*> = Generators.pick(listOf("a", "b"))
// 3.x
val value: Any = generator.generate()
// From 4.0.0
val value: Any? = generator.generate()
```

**Unchanged:** the Kotest `krandomPickArb` keeps `T : Any`, and `Generators.pickSet` and
`PickSetGenerator` keep a non-null element type.

## Changed: four seeding settings are on by default

3.2.0 added four `GeneratorConfig` settings as opt-ins. From 4.0.0 they are on by default, so seeded
output changes where they apply:

| Setting | What changes from 4.0.0 |
|---|---|
| `advancingConvenienceStreams` | `EmailGenerator.generateCompanyEmail()`, the `FullNameGenerator` methods with a middle name or initial, and `CurrencyGenerator.generatePriceTag` give the next value on each call, where 3.x repeated one value. The first call gives what it gave before. |
| `strictMathGaussian` | `NormalDistributionGenerator` draws with `StrictMath`, so a seeded value can differ in its last bit from what `Math` gave on your platform, and it is the same on every platform. `Generators.ofNormal()`, `ofNormal(mean, standardDeviation)` and the constructors without a configuration use `GeneratorConfig.defaults()`, so they draw with `StrictMath` too. |
| `objectReseedBuiltInRandomizers` | Object generation reseeds the 18 built-in `@Randomizer` generators that are not `Seedable`, such as `UUIDGenerator` and `FirstNameGenerator`, from the object's seeded stream. Their field values replay from the seed, where in 3.x they changed from run to run. Other fields keep their values. |
| `germanStreetLayout` | The locales whose language is German write a street address street first. This changes the full address, `AddressInfo`, `Krandom.streetAddress()`, the address schema columns, the object engine's street fields, and the composites built on them, such as `PersonInfo`, `OrderInfo` and `InvoiceInfo`. |

For example, with seed 42:

```java
EmailGenerator emails = new EmailGenerator(
        GeneratorConfig.builder().seed(42L).locale(Locale.US).build());
emails.generateCompanyEmail(); // aharris@advancedassociatesco.test in 3.x and from 4.0.0
emails.generateCompanyEmail(); // 3.x: aharris@advancedassociatesco.test again
                               // from 4.0.0: juliagarcia@advancedresourcesltd.test

StreetAddressGenerator streets = new StreetAddressGenerator(
        GeneratorConfig.builder().seed(42L).locale(Locale.GERMANY).build());
streets.generate(); // 3.x: 7389 Schloss Anger; from 4.0.0: Schlossanger 7389
```

### Keeping the 3.2 values

Set a setting to `false` to keep its 3.x values. With all four `false`, a seed gives what 3.2.0 gives.

Java:

```java
GeneratorConfig config = GeneratorConfig.builder()
        .seed(42L)
        .advancingConvenienceStreams(false)
        .strictMathGaussian(false)
        .objectReseedBuiltInRandomizers(false)
        .germanStreetLayout(false)
        .build();
```

The Kotlin DSL has the same functions in `krandomConfig { ... }` and `config { ... }`:

```kotlin
val config =
    krandomConfig {
        seed(42L)
        advancingConvenienceStreams(false)
        strictMathGaussian(false)
        objectReseedBuiltInRandomizers(false)
        germanStreetLayout(false)
    }

val resident = krandom<Resident> { config { seed(42L); germanStreetLayout(false) } }
```

The Spring Boot starter has a property for each from 4.0.0. Leave one unset to keep the default:

```properties
krandom.advancing-convenience-streams=false
krandom.strict-math-gaussian=false
krandom.object-reseed-built-in-randomizers=false
krandom.german-street-layout=false
```

A recipe records all four, so each property fails startup next to `krandom.recipe`, like the other
properties a recipe records. A Gaussian value drawn with `Math` can still differ in its last bit between
platforms, as it did in 3.x.

## Changed: recipes are `krandom-recipe/v2`

From 4.0.0 a portable recipe is `krandom-recipe/v2`. It records the four settings as `true` or `false`:

```text
setting.address.german-street-layout=false
setting.advancing-convenience-streams=false
setting.gaussian.strict-math=false
setting.object.reseed-built-in-randomizers=false
```

Replay requires all four, so a recipe gives the same values whatever the defaults of the release that
replays it. Every 3.x release writes `krandom-recipe/v1`, whose values differ from 4.0.0, and 4.0.0
rejects it: `GenerationRecipe.parse` and `GenerationRecipe.Builder.build()` throw an
`IllegalArgumentException` that names the `library-version` the recipe records:

```text
Unsupported recipe version: v1. kRandom 4.x replays only krandom-recipe/v2 recipes: a krandom-recipe/v1 recipe was written by kRandom 3.x or earlier, and its seeded values differ from 4.0.0. This recipe records library-version 3.2.0: replay it with kRandom 3.2.0.
```

A v1 recipe without a `library-version` ends with `This recipe records no library-version: replay it with
the 3.x release that wrote it.` instead.

To replay a 3.x recipe, run it with the 3.x release it names, for example with
`io.github.frikit:krandom-bom:3.2.0`. To move a test to 4.0.0, keep its seed and record a new recipe.

The test and Spring integrations report the same message:

- **JUnit extension:** a v1 recipe in `krandom.junit.recipe` or `krandom.junit.class-recipe` is a
  configuration error, `Invalid krandom.junit.recipe replay recipe: Unsupported recipe version: v1. ...`,
  or `Invalid krandom.junit.class-recipe replay recipe: ...`.
- **Spring Boot starter:** a v1 recipe in `krandom.recipe` fails at context startup with
  `Invalid krandom.recipe: Unsupported recipe version: v1. ...`.

A generation report names the format as `krandom-recipe/v2`.

### `GenerationRecipe.RECIPE_VERSION`

`GenerationRecipe.RECIPE_VERSION` is a compile-time constant, `"v2"` from 4.0.0. javac copies a constant
into the code that reads it, so code compiled against 3.x still holds `"v1"`:

- passed to `GenerationRecipe.builder().recipeVersion(...)`, it fails at `build()` with the v1 message
  above. That message names the builder's `library-version`, which is the running release unless the code
  sets one, so in this case it does not name a 3.x release to pin.
- compared with `getRecipeVersion()`, it no longer matches a 4.0.0 recipe.

Recompile such code against 4.0.0.

## What does not change

- **Java 17** is still the minimum for every module: the Java modules compile with `--release 17`, and the
  Kotlin modules for JVM target 17.
- **Kotlin:** `krandom-kotlin-dsl` and `krandom-kotest-extensions` are still compiled for Kotlin language
  and API version 2.2, with `kotlin-stdlib` 2.2.21.
- **Spring Boot:** `krandom-spring-boot-starter` still needs Spring Boot 4.x.
- **Maintenance:** only the latest release is maintained, and fixes are not backported to earlier ones.
- **Other public API:** the public API check against 3.2.0 accepts only the three removals above, listed in
  `core/api/accepted-breaks-4.0.txt`, and the other modules list no break. The `Schema` and `pick` type
  changes keep every JVM signature, which that check compares.

See the [versioning policy](../../VERSIONING.md) for the platform requirements and the determinism
contract.

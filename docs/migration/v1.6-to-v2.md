# Migrating from kRandom 1.6 to v2

kRandom 1.6 keeps the legacy facade entry points as thin delegates so projects can migrate before adopting v2. Replace deprecated aliases without changing fixture behavior:

| Deprecated in 1.6 | Canonical API |
|:---|:---|
| `Generators.constant(value)` | `Generators.ofConstant(value)` |
| `Generators.pickFrom(values)` | `Generators.pick(values)` |
| `Generators.pickSetFrom(values, count)` | `Generators.pickSet(values, count)` |
| `Generators.pickset(values, count)` | `Generators.pickSet(values, count)` |
| `Generators.shuffleOf(values)` | `Generators.shuffle(values)` |
| `Generators.uniqueValues(generator)` | `Generators.unique(generator)` |

The deprecated methods remain binary/source compatible in 1.6 and are planned for removal in v2. Migrate one alias family per change and keep seeded fixture assertions in place.

URL, URI, and UUID acronym factories are intentionally unchanged while their naming convention is decided.

## Config-scoped locale data

All global `register(...)` methods on data registries, plus the two `ProfessionDataRegistry.append(...)`
overloads, are deprecated for removal in v2. They retain their exact 1.6 behavior, but mutate
process-wide state and can leak custom vocabulary between tests. Register custom data on the
`GeneratorConfig` that consumes it instead:

```java
DataRegistryContext data = DataRegistryContext.builder()
    .registerFirstNameProvider(customNames)
    .build();

GeneratorConfig config = GeneratorConfig.builder()
    .registryContext(data)
    .build();

FirstNameGenerator names = new FirstNameGenerator(config);
```

Use the corresponding `DataRegistryContext.Builder.register…Provider(...)` method for every other
locale data family. Replace a profession append operation by constructing the complete merged
`ProfessionDataProvider` explicitly and registering it with `registerProfessionProvider(...)`.

## Banking identifiers and account fixtures

`GeneratorConfig` and the canonical banking facades now fail closed for account numbers, ABA
routing numbers, BBANs, IBANs, BICs, and structured bank payloads. Correct structure or a valid
checksum does not make a banking identifier safe for an external payment system. The affected
no-argument and locale constructors are deprecated 1.6 bridges and retain their prior
realistic-but-unclassified output only until v2.

For an isolated fixture that must preserve prior behavior, opt in explicitly and keep the value
inside the test boundary:

```java
GeneratorConfig config = GeneratorConfig.builder()
    .locale(Locale.US)
    .seed(42L)
    .bankingSafetyPolicy(BankingSafetyPolicy.REALISTIC_UNCLASSIFIED)
    .build();

String iban = new IbanGenerator(config).generate();
```

`PaymentInfoGenerator` remains usable with the default policy, but bank-method payloads expose only
an opaque `ACCT-TEST-####` reference. Do not use `REALISTIC_UNCLASSIFIED` as a production account,
routing number, BIC, or a claim that an identifier is non-routable.

`NationalIdGenerator` constructors are deprecated 1.6 bridges and retain their prior
realistic-but-unclassified output only until v2.

GeneratorConfig config = GeneratorConfig.builder()
    .locale(Locale.US)
    .seed(42L)

    .build();

NationalIdGenerator ids = Generators.ofNationalId(config);

non-routable.

## Corporate tax-ID fixtures

`GeneratorConfig`, `Generators.ofCnpj()`, and `Generators.ofEin()` now fail closed for corporate
tax identifiers. A plausible CNPJ or EIN must not be used for tax filing, banking, licensing, or
another external system. The no-argument `CnpjGenerator` and `EinGenerator` constructors are
deprecated 1.6 bridges and retain their prior realistic-but-unclassified output only until v2.

For an isolated fixture that must preserve prior behavior, opt in explicitly and keep the value
inside the test boundary:

```java
GeneratorConfig config = GeneratorConfig.builder()
    .seed(42L)
    .businessTaxIdentifierSafetyPolicy(BusinessTaxIdentifierSafetyPolicy.REALISTIC_UNCLASSIFIED)
    .build();

String cnpj = Generators.ofCnpj(config).generate();
String ein = Generators.ofEin(config).generate();
```

Do not use `REALISTIC_UNCLASSIFIED` as a production identifier or a claim that a generated tax ID
is non-routable. To exercise the documented 14-character alphanumeric CNPJ shape under the same
explicit compatibility policy, add `withAlphanumericFormat()`:

```java
String alphanumericCnpj = Generators.ofCnpj(config)
    .withAlphanumericFormat()
    .generate();
```

This validates only the published CNPJ shape and check digits. Receita Federal's official CNPJ
simulator has a separate fictitious-value contract; use that simulator when a fixture must carry
the authority's non-real-data claim.

## Cryptocurrency address fixtures

`GeneratorConfig` and `Generators.ofCryptoAddress()` now fail closed for cryptocurrency
destination-address shapes. A plausible address is not proof that it belongs to a test network, is
unspendable, or is safe to submit to a wallet, exchange, or blockchain service. The no-argument
`CryptoAddressGenerator` constructor is a deprecated 1.6 bridge and retains its prior
realistic-but-unclassified output only until v2.

For an isolated fixture that must preserve prior behavior, opt in explicitly and keep the value
inside the test boundary:

```java
GeneratorConfig config = GeneratorConfig.builder()
    .seed(42L)
    .cryptoAddressSafetyPolicy(CryptoAddressSafetyPolicy.REALISTIC_UNCLASSIFIED)
    .build();

String address = Generators.ofCryptoAddress(config).generate("ethereum");
```

Do not use `REALISTIC_UNCLASSIFIED` as a production destination or a claim that a generated
address is non-routable. Use the selected blockchain's testnet or a local development network when
a test requires transactions rather than only a text fixture.

## Object construction

V2 object generation defaults to `ObjectConstructionPolicy.SAFE_CONSTRUCTORS`. Records use their
canonical constructor; ordinary classes use a no-argument constructor or one unambiguous declared
constructor. Constructor parameters use the same type and Bean Validation rules as fields.

If a 1.x fixture relied on constructor bypass, prefer a type factory:

```java
GeneratorConfig config = GeneratorConfig.builder()
    .objectOverride(LegacyFixture.class, LegacyFixture::createForTest)
    .build();
```

As a temporary bridge only, opt into the old fallback explicitly:

```java
GeneratorConfig config = GeneratorConfig.builder()
    .objectConstructionPolicy(ObjectConstructionPolicy.UNSAFE_CONSTRUCTOR_BYPASS)
    .build();
```

This unsafe mode can skip constructor invariants and field initializers. Named modules must still
open fixture packages for reflective field population:

```java
opens com.example.fixtures to io.github.frikit.krandom;
```

## Immutable Kotlin fixtures

Use `krandom-kotlin-dsl` for immutable Kotlin data classes and primary-constructor classes. It adds
Kotlin reflection without making Java-only `krandom-core` consumers depend on Kotlin:

```kotlin
data class User(val name: String, val source: String = "test")

val user = krandom<User> { rule("name") { "Ada" } }
```

Optional constructor parameters preserve their Kotlin defaults until a field or type rule explicitly
targets them. `@param:` and `@field:` Jakarta Validation constraints apply to constructor values.
The primary constructor is always used; delegated properties initialize normally and required
immutable cycles fail before returning a partial value. Value classes and sealed/abstract Kotlin
types require an explicit override or concrete subtype.

# Migrating from kRandom 1.x to 2.0.0

2.0.0 removes legacy 1.x facade entry points. Replace each removed alias with its canonical
equivalent without changing fixture behavior:

| 1.x API | 2.0.0 API |
|:---|:---|
| `Generators.constant(value)` | `Generators.ofConstant(value)` |
| `Generators.pickFrom(values)` | `Generators.pick(values)` |
| `Generators.pickSetFrom(values, count)` | `Generators.pickSet(values, count)` |
| `Generators.pickset(values, count)` | `Generators.pickSet(values, count)` |
| `Generators.shuffleOf(values)` | `Generators.shuffle(values)` |
| `Generators.uniqueValues(generator)` | `Generators.unique(generator)` |

Migrate one alias family per change and keep seeded fixture assertions in place.

URL, URI, and UUID acronym factories are intentionally unchanged while their naming convention is decided.

## Typed reseeding

`Generator.reseed(long)` and `Generator.reseed(String)` are removed in 2.0.0. Their reflection
fallback mutated `Random` state the generator does not own, which cannot preserve the 2.0.0 replay
contract: it could reseed the wrong field, silently reseed a caller-owned or secure source, or
throw for generators without an accessible `Random`. Reseed through the typed `Seedable` contract
instead:

```java
if (generator instanceof Seedable seedable) {
    seedable.reseed(42L);                                    // numeric seed
    seedable.reseed(GeneratorConfig.deriveSeed("checkout")); // textual seed
}
```

Generators that do not implement `Seedable` are not reseedable in 2.0.0; construct a new generator
from a seeded `GeneratorConfig` instead of mutating an existing instance.

## Strict bounds

Bounded generation rejects `min >= max` with `IllegalArgumentException("min must be less than
max, ...")` instead of silently swapping reversed bounds. Audit call sites that passed reversed
bounds — under 1.x they produced values from the swapped range; under 2.0.0 they fail immediately.

## Explicit safety policies for finance and identity generators

The no-argument and `Locale` constructors from 1.x are removed in 2.0.0: they silently selected
`REALISTIC_UNCLASSIFIED` output. Construct these generators with a
`GeneratorConfig` that states the safety policy, for example:

```java
NationalIdGenerator generator = new NationalIdGenerator(
    GeneratorConfig.builder()
                   .locale(Locale.ITALY)
                   .seed(seed)
                   .nationalIdSafetyPolicy(NationalIdSafetyPolicy.REALISTIC_UNCLASSIFIED)
                   .build());
```

The same pattern applies with `bankingSafetyPolicy`, `securitiesIdentifierSafetyPolicy`,
`cryptoAddressSafetyPolicy`, `businessTaxIdentifierSafetyPolicy`, and
`identityDocumentSafetyPolicy` for the other removed constructors. Default configurations without
a policy fail closed instead of producing realistic identifiers.

## Config-scoped locale data

All global `register(...)` methods on data registries, the two `ProfessionDataRegistry.append(...)`
overloads, and `LocaleDataBundle.registerGlobal()` are removed in 2.0.0. They mutated process-wide
state and could leak custom vocabulary between tests. Built-in locale data still loads
automatically and read-only lookups (`forLocale`, `isRegistered`, `registeredKeys`) are
unchanged. Register custom data on the `GeneratorConfig` that consumes it instead:

```java
DataRegistryContext data = DataRegistryContext.builder()
    .registerFirstNameProvider(customNames)
    .build();

GeneratorConfig config = GeneratorConfig.builder()
    .registryContext(data)
    .build();

FirstNameGenerator names = new FirstNameGenerator(config);
```

Use the corresponding `DataRegistryContext.Builder.register…Provider(...)` method for every other
locale data family. Replace a profession append operation by constructing the complete merged
`ProfessionDataProvider` explicitly and registering it with `registerProfessionProvider(...)`.

## Banking identifiers and account fixtures

`GeneratorConfig` and the canonical banking facades now fail closed for account numbers, ABA
routing numbers, BBANs, IBANs, BICs, and structured bank payloads. Correct structure or a valid
checksum does not make a banking identifier safe for an external payment system. The affected
no-argument and locale constructors from 1.x are removed. Use an explicit policy for every
realistic-but-unclassified fixture.

For an isolated fixture that must preserve prior behavior, opt in explicitly and keep the value
inside the test boundary:

```java
GeneratorConfig config = GeneratorConfig.builder()
    .locale(Locale.US)
    .seed(42L)
    .bankingSafetyPolicy(BankingSafetyPolicy.REALISTIC_UNCLASSIFIED)
    .build();

String iban = new IbanGenerator(config).generate();
```

`PaymentInfoGenerator` remains usable with the default policy, but bank-method payloads expose only
an opaque `ACCT-TEST-####` reference. Do not use `REALISTIC_UNCLASSIFIED` as a production account,
routing number, BIC, or a claim that an identifier is non-routable.

## National-ID fixtures

`GeneratorConfig` and the canonical `Generators.ofNationalId(GeneratorConfig)` path now fail
closed for national IDs. National-ID shape or checksum validity does not make an identifier safe
to use in account creation, KYC, payment, or any external system. The locale and seeded
`NationalIdGenerator` constructors from 1.x are removed. Use an explicit policy for every
realistic-but-unclassified fixture.

For an isolated fixture that must preserve prior behavior, opt in explicitly and keep the value
inside the test boundary:

```java
GeneratorConfig config = GeneratorConfig.builder()
    .locale(Locale.US)
    .seed(42L)
    .nationalIdSafetyPolicy(NationalIdSafetyPolicy.REALISTIC_UNCLASSIFIED)
    .build();

NationalIdGenerator ids = Generators.ofNationalId(config);
```

Do not use `REALISTIC_UNCLASSIFIED` as a production credential or a claim that the generated ID is
non-routable.

## Passport and driving-license fixtures

`GeneratorConfig`, `Generators.ofPassport()`, and `Generators.ofDrivingLicense()` fail closed
for generic document identifiers. A plausible passport or driving-license shape is not evidence

system. The no-argument `PassportGenerator` and `DrivingLicenseGenerator` constructors from 1.x
are removed.

```java
GeneratorConfig config = GeneratorConfig.builder()
    .seed(42L)
    .identityDocumentSafetyPolicy(IdentityDocumentSafetyPolicy.REALISTIC_UNCLASSIFIED)
    .build();

String passport = Generators.ofPassport(config).generate();
```

Do not use `REALISTIC_UNCLASSIFIED` as a production credential or a claim that the generated

## Corporate tax-ID fixtures

`GeneratorConfig`, `Generators.ofCnpj()`, and `Generators.ofEin()` now fail closed for corporate
tax identifiers. A plausible CNPJ or EIN must not be used for tax filing, banking, licensing, or
another external system. The no-argument `CnpjGenerator` and `EinGenerator` constructors from 1.x
are removed.

For an isolated fixture that must preserve prior behavior, opt in explicitly and keep the value
inside the test boundary:

```java
GeneratorConfig config = GeneratorConfig.builder()
    .seed(42L)
    .businessTaxIdentifierSafetyPolicy(BusinessTaxIdentifierSafetyPolicy.REALISTIC_UNCLASSIFIED)
    .build();

String cnpj = Generators.ofCnpj(config).generate();
String ein = Generators.ofEin(config).generate();
```

Do not use `REALISTIC_UNCLASSIFIED` as a production identifier or a claim that a generated tax ID
is non-routable. To exercise the documented 14-character alphanumeric CNPJ shape under the same
explicit compatibility policy, add `withAlphanumericFormat()`:

```java
String alphanumericCnpj = Generators.ofCnpj(config)
    .withAlphanumericFormat()
    .generate();
```

This validates only the published CNPJ shape and check digits. Receita Federal's official CNPJ
simulator has a separate fictitious-value contract; use that simulator when a fixture must carry
the authority's non-real-data claim.

## Cryptocurrency address fixtures

`GeneratorConfig` and `Generators.ofCryptoAddress()` now fail closed for cryptocurrency
destination-address shapes. A plausible address is not proof that it belongs to a test network, is
unspendable, or is safe to submit to a wallet, exchange, or blockchain service. The no-argument
`CryptoAddressGenerator` constructor from 1.x is removed.

For an isolated fixture that must preserve prior behavior, opt in explicitly and keep the value
inside the test boundary:

```java
GeneratorConfig config = GeneratorConfig.builder()
    .seed(42L)
    .cryptoAddressSafetyPolicy(CryptoAddressSafetyPolicy.REALISTIC_UNCLASSIFIED)
    .build();

String address = Generators.ofCryptoAddress(config).generate("ethereum");
```

Do not use `REALISTIC_UNCLASSIFIED` as a production destination or a claim that a generated
address is non-routable. Use the selected blockchain's testnet or a local development network when
a test requires transactions rather than only a text fixture.

## Securities-identifier fixtures

`GeneratorConfig`, `Generators.ofIsin()`, and `Generators.ofCusip()` now fail closed for ISIN and
CUSIP output. A valid check digit does not establish that an identifier is unassigned,
non-routable, or safe to submit to a trading, custody, clearing, or settlement system. The
no-argument and locale `IsinGenerator` constructors, and the no-argument `CusipGenerator`
constructor from 1.x, are removed.

For an isolated fixture that must preserve prior behavior, opt in explicitly and keep the value
inside the test boundary:

```java
GeneratorConfig config = GeneratorConfig.builder()
    .seed(42L)
    .securitiesIdentifierSafetyPolicy(SecuritiesIdentifierSafetyPolicy.REALISTIC_UNCLASSIFIED)
    .build();

String isin = Generators.ofIsin(config).generate();
String cusip = Generators.ofCusip(config).generate();
```

Do not use `REALISTIC_UNCLASSIFIED` as a production security identifier or a claim that a generated
value is safe for an external financial system. Use the institution's documented sandbox or test
instrument data when an integration needs more than a text fixture.

## Object construction

2.0.0 object generation defaults to `ObjectConstructionPolicy.SAFE_CONSTRUCTORS`. Records use their
canonical constructor; ordinary classes use a no-argument constructor or one unambiguous declared
constructor. Constructor parameters use the same type and Bean Validation rules as fields.

If a 1.x fixture relied on constructor bypass, prefer a type factory:

```java
GeneratorConfig config = GeneratorConfig.builder()
    .objectOverride(LegacyFixture.class, LegacyFixture::createForTest)
    .build();
```

As a temporary bridge only, opt into the old fallback explicitly:

```java
GeneratorConfig config = GeneratorConfig.builder()
    .objectConstructionPolicy(ObjectConstructionPolicy.UNSAFE_CONSTRUCTOR_BYPASS)
    .build();
```

This unsafe mode can skip constructor invariants and field initializers. Named modules must still
open fixture packages for reflective field population:

```java
opens com.example.fixtures to io.github.frikit.krandom;
```

## Immutable Kotlin fixtures

Use `krandom-kotlin-dsl` for immutable Kotlin data classes and primary-constructor classes. It adds
Kotlin reflection without making Java-only `krandom-core` consumers depend on Kotlin:

```kotlin
data class User(val name: String, val source: String = "test")

val user = krandom<User> { rule("name") { "Ada" } }
```

Optional constructor parameters preserve their Kotlin defaults until a field or type rule explicitly
targets them. `@param:` and `@field:` Jakarta Validation constraints apply to constructor values.
The primary constructor is always used; delegated properties initialize normally and required
immutable cycles fail before returning a partial value. Value classes and sealed/abstract Kotlin
types require an explicit override or concrete subtype.
